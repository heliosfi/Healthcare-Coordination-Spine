v0 System Definition

Healthcare Coordination Spine

Freeze the concept before code. One bounded workflow, four authority domains, one coordination state.

1. Purpose

Make the product do one thing clearly before APIs, vendors, HIPAA implementation, or UI spread the scope.

2. Boundaries (locked for v0)

  • Primary problem: patients, doctors, pharmacies, and insurers can each hold valid information while still being out of sync about the current care state.
  • First use case: prescription coordination.
  • Core question: Where is the prescription, what is blocking it, and who is responsible for the next action?
  • System role: coordinate authoritative information; do not replace the EHR, pharmacy system, insurer, or clinician.
Governance rule: access does not create authority.
Safety rule: the system may explain or route information, but it does not independently diagnose, prescribe, discontinue medication, or reinterpret a clinician's order.
Evidence rule: every consequential state must identify its source, timestamp, responsible organization, and whether it is verified, disputed, pending, or unknown.

5. Authority matrix

Actor Can originate Can update Can view as needed
Patient consent, preferences, patient-reported information own inputs permitted care/coverage state
Doctor orders, diagnosis, clinical documentation clinical objects they control relevant patient/coverage/pharmacy status
Pharmacy dispense/fulfillment state pharmacy-controlled events prescription + required coverage information
Insurer coverage, PA, claim state payer-controlled decisions information needed for covered workflow
Coordination Spine workflow state, provenance, alerts coordination metadata referenced source data only as authorized
The Spine must not overwrite the authoritative source just because systems disagree.

6. Conflict becomes a state

Disagreement is not an error to hide — it is a coordination state to manage.

CONFLICT_DETECTED → HOLD → SOURCE_RECONCILIATION → VERIFIED_STATE

7. Architectural order (after freeze)

  1. data model
  2. authority/consent contract
  3. event/state machine
  4. audit/provenance contract
  5. UI
  6. integration adapters

8. Out of scope for core v0

  • Keep FHIR, TEFCA, payer APIs, and NCPDP outside the core as adapters, so coordination logic doesn't become dependent on one transport standard.
One bounded workflow, four authority domains, one coordination state, and no invented medical authority.
