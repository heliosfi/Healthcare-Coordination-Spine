# Healthcare Coordination Spine — v0.1 State-Transition Contract

Conversation-derived design contract carried into the repository under N.B.C. authority on 2026-10-03. This specifies coordination behavior; no transition engine is implemented. Corrections and remaining prerequisites are recorded in [specification status](../specification-status.md).

## 1. Purpose

Determine whether a source-attributed event may change verified prescription coordination state after source identity, authority, and required consent checks.

Event received → source validation → authority/consent → transition validation → `PROMOTE | REJECT | HOLD` → audit/provenance.

This does not determine clinical appropriateness, medical necessity, prescription validity, dispensing legality, or treatment effectiveness.

## 2. Core rule

```text
EVENT_RECEIVED ≠ EVENT_AUTHORIZED ≠ TRANSITION_VALID ≠ STATE_PROMOTED
```

All applicable guards must pass before promotion.

## 3. Transition result

| Result | Meaning |
|---|---|
| PROMOTE | Authorized, attributable, permitted transition with required evidence and no blocking conflict |
| REJECT | Confirmed invalid source authority or transition under this workflow contract |
| HOLD | Required evidence, authority, consent, sequencing, or reconciliation remains unresolved; promotion is blocked |

A pharmacy attempt to establish `PAYER_REVIEW → APPROVED` yields REJECT, reason `SOURCE_LACKS_PAYER_AUTHORITY`. An unresolved transition yields HOLD and `promotion_blocked = true`.

REJECT describes a rejected promotion, not deletion of the source assertion. Authorization DENY prevents entering the promotion evaluator; its audit record remains separate.

## 4. Transition guards

```text
G1_SOURCE_IDENTIFIED
G2_ACTOR_AUTHORIZED
G3_PURPOSE_VALID
G4_REQUIRED_CONSENT_SATISFIED
G5_CURRENT_STATE_MATCHES
G6_TRANSITION_ALLOWED
G7_REQUIRED_EVIDENCE_PRESENT
G8_NO_BLOCKING_CONFLICT
G9_EVENT_NOT_STALE
G10_EVENT_NOT_DUPLICATE
```

All required guards passing permits PROMOTE. A confirmed invalid authority or transition produces REJECT. Required unresolved information produces HOLD.

Guard outcomes need PASS, FAIL, and UNRESOLVED distinctions. A missing source fact is HOLD when it could still establish an otherwise allowed transition; a confirmed prohibited inference is REJECT. Conflicting simultaneous failures require a deterministic precedence policy before implementation.

## 5. Canonical path and exception loop

| Segment | Allowed progression |
|---|---|
| Intake | PRESCRIBED → PRESCRIPTION_RECEIVED → COVERAGE_CHECK |
| No PA branch | COVERAGE_CHECK → PA_NOT_REQUIRED → PHARMACY_PROCESSING |
| PA branch | COVERAGE_CHECK → PA_REQUIRED → PA_SUBMITTED → PAYER_REVIEW → APPROVED → PHARMACY_PROCESSING |
| More information | PAYER_REVIEW → NEEDS_INFORMATION → PROVIDER_ACTION → PAYER_REVIEW |
| Fulfillment | PHARMACY_PROCESSING → READY → DISPENSED |
| Successful completion with receipt required | DISPENSED → PATIENT_RECEIPT_KNOWN → FOLLOW_UP → CLOSED |

Conflict interrupts promotion through `CONFLICT_DETECTED`, HOLD, reconciliation, then qualification as `VERIFIED_STATE`. These are governance labels, not clinical facts or replacement prescription states.

## 6. Transition table

Each row is eligible for PROMOTE only when all required guards pass. Transport alternatives require a verified originating actor and authority basis.

| From | Event / evidence | Required source authority | To |
|---|---|---|---|
| Workflow start | Prescription created | PRESCRIBER | PRESCRIBED |
| PRESCRIBED | Destination prescription receipt confirmed | PHARMACY; routing source only with attributable destination acknowledgement | PRESCRIPTION_RECEIVED |
| PRESCRIPTION_RECEIVED | Coverage inquiry initiated | Actor authorized for scoped coverage inquiry | COVERAGE_CHECK |
| COVERAGE_CHECK | PA not required | PAYER-authoritative coverage evidence | PA_NOT_REQUIRED |
| COVERAGE_CHECK | PA required | PAYER-authoritative coverage evidence | PA_REQUIRED |
| PA_REQUIRED | PA submission confirmed | PRESCRIBER; submission system preserving authenticated origin | PA_SUBMITTED |
| PA_SUBMITTED | Review acknowledged | PAYER | PAYER_REVIEW |
| PAYER_REVIEW | More information required | PAYER | NEEDS_INFORMATION |
| NEEDS_INFORMATION | Required information submitted | PRESCRIBER | PROVIDER_ACTION |
| PROVIDER_ACTION | Review resumed | PAYER | PAYER_REVIEW |
| PAYER_REVIEW | PA approved | PAYER | APPROVED |
| PAYER_REVIEW | PA denied | PAYER | DENIED |
| PA_NOT_REQUIRED | Processing begins | PHARMACY | PHARMACY_PROCESSING |
| APPROVED | Processing begins | PHARMACY | PHARMACY_PROCESSING |
| PHARMACY_PROCESSING | Prescription ready | PHARMACY | READY |
| READY | Prescription dispensed | PHARMACY | DISPENSED |
| DISPENSED | Receipt confirmed | PATIENT; other attributable confirmation requires an explicitly defined policy | PATIENT_RECEIPT_KNOWN |
| PATIENT_RECEIPT_KNOWN | Required follow-up begins | PRESCRIBER / explicitly scoped workflow authority | FOLLOW_UP |
| FOLLOW_UP | Closure predicates satisfied | SPINE coordination attestation | CLOSED |

No edge is a clinical directive. The table covers the receipt-confirmation path; optional receipt/follow-up bypass edges require explicit workflow definitions and remain unresolved, rather than being silently inferred.

## 7. No-skip rule

The Spine MUST NOT invent intermediate consequential states. Receiving PA_REQUIRED and an approval does not establish observed PA_SUBMITTED or PAYER_REVIEW.

If a configured, versioned workflow explicitly allows authoritative approval evidence to establish APPROVED directly, it may mark intermediate milestones `not_observed`, retain evidence, and evaluate that documented alternate edge. Without such an edge and its guards, missing sequence evidence yields HOLD. The displayed transition table does not itself implement a bypass.

## 8. No backward rewrite

`NEEDS_INFORMATION → PROVIDER_ACTION → PAYER_REVIEW → APPROVED` does not erase the earlier request. Retained provenance is append-only: history differs from current state. Source corrections are additional attributed records, not silent historical edits.

## 9. Stale event guard

For late NEEDS_INFORMATION received after APPROVED and PHARMACY_PROCESSING, evaluate source-event time, source sequence/version, effective period, authority, instance identifiers, current verified state, and conflict implications. Arrival order alone is insufficient.

| Classification | Handling |
|---|---|
| Proven historical event | Preserve permitted provenance; REJECT current-state promotion with `STALE_EVENT`; no regression |
| Genuine unresolved contradiction | Record conflict and HOLD |
| Ordering cannot be established | HOLD with `ORDERING_UNRESOLVED` |

An authoritative new revocation is not necessarily stale because it looks like an earlier status. Reversal/revocation routes are outside the current successful-path table and must not be invented.

## 10. Duplicate event guard

Repeated delivery is idempotent. The conceptual identity inputs are `event_id`, `source_system`, `source_event_id`, `coordination_id`, `event_type`, and timestamp; the actual uniqueness key and canonical payload comparison remain for Audit & Provenance.

A proven duplicate returns:

```text
result = REJECT
reason_code = DUPLICATE_EVENT
state_changed = false
```

This explicitly rejects a second promotion attempt while preserving the already accepted original. It normalizes the earlier draft's `NO_STATE_CHANGE` result into the declared three-result enum. No duplicate transition or responsibility handoff is generated. Reusing an identity with incompatible content is an unresolved identity conflict, not a benign duplicate; HOLD pending investigation.

## 11. Conflict interruption

If verified NEEDS_INFORMATION conflicts with a received APPROVED claim, both claims remain attributable. Set `conflict.resolution_state = HOLD` and `promotion_blocked = true`.

The last verified `current_state` remains intact. The conflict object and patient-facing qualification expose the hold; the disputed approval must not be presented as verified readiness. The enum's conflict labels describe that governance process, not an instruction to overwrite `current_state.status` with HOLD.

Upstream publication and pharmacy behavior remain outside the Spine's independent control.

## 12. Reconciliation transition

Reconciliation identifies the claim competent to govern coordination, without creating the underlying fact. Authority and evidence comparison establish a governing source claim only when the disputed prescription, PA instance, scope, and effective time agree.

```text
ReconciliationOutput {
  winning_source
  winning_value
  conflicting_source_refs[]
  authority_basis
  evidence_basis
  resolved_at
  resolved_by
}
```

The original vocabulary `winning_source` and `winning_value` names the governing claim, not a blanket vendor hierarchy. If competence or evidence remains unresolved, HOLD persists. The non-governing claim remains in retained provenance.

`VERIFIED_STATE` describes successful evidence qualification. Resuming a concrete prescription state still requires a valid transition and guards; reconciliation does not authorize bypassing consent, sequencing, or closure requirements.

## 13. Responsibility handoff

On PAYER_REVIEW → APPROVED, the approval fact retains PAYER authority while responsibility moves to PHARMACY. On READY, source authority is PHARMACY and responsibility is PATIENT, with pickup as the bounded patient action.

Each promoted transition records old/new responsibility. It never transfers clinical, payer, or pharmacy authority with that handoff.

## 14. Patient receipt boundary

DISPENSED → PATIENT_RECEIPT_KNOWN requires patient-originated or otherwise explicitly attributable receipt evidence permitted by a defined policy. Patient-entered confirmation remains `confidence = patient-reported`.

DISPENSED alone establishes neither possession, ingestion, adherence, nor clinical effect.

## 15. Follow-up boundary

FOLLOW_UP represents coordination follow-up only. It does not establish treatment effectiveness, adherence, clinical goal achievement, or condition resolution. Those require their own clinical evidence and are outside this workflow unless separately specified.

## 16. Closure transition

Only the Spine promotes FOLLOW_UP → CLOSED because CLOSED is a coordination conclusion. Required predicates are no active HOLD/conflict/reconciliation; no outstanding required action; null responsible actor; branch-specific milestones and required follow-up satisfied; complete, attributable closure basis.

The transition atomically clears the completed required action and responsible actor in the proposed CLOSED object when the evidence satisfies closure predicates. It does not require an unrecorded pre-closure state mutation.

Required output: `status = CLOSED`, `source = Spine`, `responsible_actor = null`, `next_required_action = null`, `patient_action = "None"`, `closure_reason`, `closed_at`, `closure_basis[]`, and provenance references.

The Spine attests to workflow completion, not medical success. CLOSED has no outgoing edge in this contract; reopening, corrections after closure, or a new episode need separate policies.

## 17. DENIED is not CLOSED

DENIED is a payer outcome, not successful coordination completion. Appeal, alternative medication, modification, cancellation, abandonment, and expiry routes require later explicit contracts. No DENIED → CLOSED edge exists here.

## 18. Invalid transition examples

| Attempt | Result | Reason |
|---|---|---|
| Pharmacy establishes payer approval | REJECT | `INVALID_SOURCE_AUTHORITY` |
| Patient changes dose by READY → PRESCRIBED | REJECT | `PATIENT_LACKS_PRESCRIBER_AUTHORITY` |
| Spine invents APPROVED → DISPENSED without pharmacy evidence | REJECT | `PROHIBITED_SOURCE_FACT_INFERENCE` |
| Otherwise plausible transition awaiting pharmacy evidence | HOLD | `REQUIRED_SOURCE_EVENT_MISSING` |
| Payer approval promotion while incompatible evidence remains unresolved | HOLD | `BLOCKING_CONFLICT` |

The distinction is known prohibited inference versus missing evidence for a potentially valid operation. No source assertion is converted into dispensing permission by these examples.

## 19. Transition decision object

```text
TransitionDecision {
  transition_id
  coordination_id
  from_state
  requested_to_state
  event_ref
  source_system
  source_authority
  authorization_decision
  guards: {
    source_identified
    actor_authorized
    purpose_valid
    consent_satisfied
    current_state_valid
    transition_allowed
    evidence_present
    conflict_clear
    event_fresh
    event_unique
  }
  result: PROMOTE | REJECT | HOLD
  reason_code
  evaluated_at
}
```

Guard fields carry PASS / FAIL / UNRESOLVED classifications, not ambiguous booleans. `purpose_valid` completes G3, which was listed in the conversation guard set but missing from its example object. These are conceptual types, not a formal schema.

## 20. Promotion event

```text
StatePromotion {
  prior_state
  promoted_state
  source_event_ref
  authority_basis
  prior_responsible_actor
  new_responsible_actor
  promoted_at
  provenance_ref
}
```

Promotion records are immutable retained records. Atomic persistence, concurrency/version checks, policy version attribution, and recovery behavior require Audit & Provenance and implementation contracts before runtime use.

## 21. Invariants

```text
SOURCE EVENT ≠ VERIFIED STATE
AUTHORIZED EVENT ≠ VALID TRANSITION
RESPONSIBILITY ≠ AUTHORITY
LATE EVENT ≠ AUTOMATIC REGRESSION
DISPENSED ≠ RECEIVED
RECEIVED ≠ TAKEN
TAKEN ≠ EFFECTIVE
APPROVED ≠ DISPENSED
DENIED ≠ CLOSED
CONFLICT ⇒ PROMOTION BLOCKED
UNKNOWN REQUIRED AUTHORITY ⇒ HOLD
UNKNOWN REQUIRED CONSENT ⇒ HOLD
CLOSED ⇒ NO OUTSTANDING REQUIRED ACTION
```
