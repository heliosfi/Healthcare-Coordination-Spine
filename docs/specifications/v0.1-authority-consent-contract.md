# Healthcare Coordination Spine — v0.1 Authority & Consent Contract

Conversation-derived design contract carried into the repository under N.B.C. authority on 2026-10-03. This is a specification, not an implemented authorizer. Editorial clarifications are recorded in [specification status](../specification-status.md).

## 1. Purpose

Determine whether an authenticated actor may perform a requested operation against a Healthcare Coordination Spine object.

This governs authorization only. It does not diagnose, prescribe, approve insurance coverage, dispense medication, reinterpret clinical information, or replace an originating healthcare system's authority.

**Responsibility moves. Authority does not.**

## 2. Authorization input

Every consequential operation MUST use an explicit authorization context:

```text
AuthorizationContext {
  actor_id
  actor_role
  actor_organization
  patient_ref
  purpose
  resource_type
  resource_id
  requested_action
  source_system
  source_authority
  consent_context
  workflow_id
  workflow_state
  provenance_ref
  timestamp
}
```

Possession of data and technical access are insufficient authorization bases.

```text
READ_ACCESS ≠ WRITE_AUTHORITY
WRITE_AUTHORITY ≠ TRANSITION_AUTHORITY
TRANSITION_AUTHORITY ≠ CLINICAL_AUTHORITY
RESPONSIBILITY ≠ AUTHORITY
```

The requested operation must distinguish reading, originating a source fact, attesting, requesting an action, and promoting coordination state. Authority must be scoped to the actual actor, organization, patient, resource, and purpose; a role label alone is insufficient. Final action vocabulary and policy bindings remain implementation prerequisites.

## 3. Decision output

Each authorization evaluation produces exactly one decision and a machine-readable reason:

```text
AuthorizationDecision {
  decision: ALLOW | DENY | HOLD
  reason_code
  evaluated_actor
  evaluated_action
  authority_basis
  consent_basis
  workflow_context
  evaluated_at
}
```

| Example result | Reason |
|---|---|
| ALLOW | `ACTOR_IS_SOURCE_AUTHORITY` |
| DENY | `ROLE_CANNOT_MODIFY_PAYER_STATE` |
| HOLD | `CONSENT_CONTEXT_UNRESOLVED` |

The ALLOW example presupposes all other applicable checks have passed. It does not bypass consent or transition guards.

## 4. Fail-closed rule

Missing or contradictory authority MUST NOT become implicit permission.

| Condition | Result |
|---|---|
| Authority confirmed | Evaluate the requested action and remaining checks |
| Authority missing | HOLD |
| Authority conflict | HOLD |
| Required consent unresolved | HOLD |
| Source unresolved | HOLD |
| Confirmed action outside actor authority | DENY |

`HOLD` prevents the requested operation from proceeding. For state-changing requests, it prevents promotion into verified coordination state pending reconciliation. For read requests, it withholds disclosure. `DENY` likewise does not disclose or mutate the requested resource.

An attempted event MAY be retained in a separately authorized audit/quarantine path; authorization to retain sensitive payloads cannot be inferred from the existence of an attempted request. Audit/provenance rules are a separate pending contract.

## 5. Actor authority

| Actor | May originate / attest | Must not originate |
|---|---|---|
| PATIENT | Preferences, consent choices, patient-reported receipt and bounded patient-reported facts | Prescriptions, clinical orders, payer decisions, pharmacy dispense events |
| PRESCRIBER | Prescriptions, clinical orders, clinical documentation, PA supporting clinical information | Payer coverage decisions, pharmacy dispensing state |
| PHARMACY | Prescription receipt, pharmacy processing, readiness and dispensing events | Clinical orders, payer approval |
| PAYER | Eligibility, coverage, PA requirements and decisions, payer-controlled states | Prescriptions, pharmacy dispense events |
| SPINE | Coordination metadata, provenance, responsibility assignment, conflicts, holds, verified-state promotion and closure | Source clinical facts, payer decisions, prescriptions, pharmacy facts |

These are source-domain capabilities subject to authenticated identity and scoped authorization. Technical integration services and transport systems do not automatically acquire them.

## 6. Source authority

Every consequential fact MUST retain its originating authority domain.

```text
PA_APPROVED:
  source_system = Health Plan X
  source_authority = PAYER

DISPENSED:
  source_system = Pharmacy
  source_authority = PHARMACY
```

A pharmacy event cannot rewrite a payer decision. Pharmacy dispensing does not establish medication ingestion. The Spine references related facts without merging their authorities.

A network may relay a payer-authenticated decision. Verification must identify the original decision-maker and any scoped delegation; the transport name alone cannot decide authority.

## 7. Purpose boundary

Authorization MUST be tied to a declared purpose:

```text
treatment
payment
pharmacy_fulfillment
patient_access
care_coordination
workflow_reconciliation
```

A role valid for purpose A is not valid for every purpose. Purpose is part of every decision and audit record. These labels describe design intent, not a determination of a legal basis for access.

## 8. Consent context

Consent is separate from authority:

```text
ConsentContext {
  consent_id
  patient_ref
  scope
  permitted_actor_or_organization
  permitted_purpose
  permitted_resource_scope
  effective_from
  effective_until
  status
}

status:
  ACTIVE
  REVOKED
  EXPIRED
  UNRESOLVED
  NOT_REQUIRED_BY_WORKFLOW
```

The Spine MUST NOT infer consent from record availability. Where consent is required:

| Consent status | Authorization handling |
|---|---|
| ACTIVE | Continue evaluation after matching patient, actor/organization, purpose, resource scope and effective interval |
| REVOKED | DENY |
| EXPIRED | DENY |
| UNRESOLVED | HOLD |

`NOT_REQUIRED_BY_WORKFLOW` is retained from the conversation vocabulary. It is usable only with an explicit, attributable policy basis establishing that consent is not required for the particular operation. A workflow author cannot use this label to waive applicable requirements. An unresolved basis produces HOLD. Applicable access/consent policy remains a prerequisite before real-data operation.

Consent itself never creates clinical, payer, or pharmacy authority.

## 9. Responsibility handoff

`responsible_actor` answers who owns the next coordination step, not who owns the underlying fact.

| State | Source authority | Next responsible actor |
|---|---|---|
| APPROVED | PAYER | PHARMACY |
| READY | PHARMACY | PATIENT |

Payer approval remains a payer fact after pharmacy responsibility begins. Patient pickup responsibility does not confer pharmacy or prescribing authority.

## 10. Transition authorization

An actor authorized to originate an event is not thereby authorized to determine the entire next coordination state. After an attributable pharmacy `READY` event, the Spine separately evaluates current state, source authority, authorization result, conflict state, and consent context.

**EVENT_ACCEPTED ≠ STATE_PROMOTED.**

ALLOW permits evaluation of the named operation. It does not establish a valid transition, clinical permission, or authority for a subsequent action.

## 11. Conflict governance

Incompatible consequential source assertions are both recorded as attributable claims, subject to permitted retention. Last-write-wins is prohibited.

`CONFLICT_DETECTED` → `HOLD` (`promotion_blocked = true`) → `SOURCE_RECONCILIATION` → `VERIFIED_STATE`.

Reconciliation establishes which authority is competent for the disputed fact. The non-governing claim is not deleted from retained provenance. Equal authority, unresolved delegation, different effective periods, and different prescription/PA instances cannot be settled by brand ranking or newest arrival alone.

## 12. Closure authorization

`CLOSED` is reserved for successful coordination completion. The Spine MAY promote only when all required closure predicates pass:

- No active conflict, HOLD, or unresolved reconciliation.
- No unresolved required action; `next_required_action = null`.
- `responsible_actor = null`.
- Branch-specific required milestones and follow-up are satisfied.
- Closure evidence is attributable.

Closure contains `status = CLOSED`, `source = Spine`, `responsible_actor = null`, `next_required_action = null`, `closure_reason`, `closed_at`, `closure_basis[]`, and provenance references.

`source = Spine` attests to coordination predicates only, not origin of underlying facts. Denial, cancellation, abandonment, expiration, and therapy discontinuation MUST NOT be relabeled successful CLOSED. See the [data-model closure completion](v0.1-data-model.md#7-authorized-closure-completion).

## 13. Audit requirement

Every consequential authorization evaluation MUST be attributable:

```text
AuditEvent {
  actor
  organization
  patient_ref
  requested_action
  affected_resource
  purpose
  authorization_decision
  reason_code
  authority_basis
  consent_basis
  prior_state
  resulting_state
  provenance_ref
  timestamp
}
```

Denied and held operations still generate an audit decision. Payload retention, access, redaction, and retention periods remain pending; this does not authorize unrestricted retention of denied input.

## 14. Core enforcement invariants

```text
access does not create authority
responsibility does not transfer authority
source data is never silently overwritten
conflict blocks promotion
unknown required authority fails closed
unknown required consent fails closed
events remain attributable
transport is not authority
AI explanation is not clinical authority
state promotion requires authorization
closure requires evidence
```

## 15. Engineering boundary

External event → source/identity validation → authority/consent decision (`ALLOW | DENY | HOLD`) → separate state-transition decision (`PROMOTE | REJECT | HOLD`) → audit/provenance.

DENY and HOLD do not proceed to promotion. All outcomes remain attributable subject to audit rules. The [State-Transition Contract](v0.1-state-transition-contract.md) defines allowed edges and guards; the Audit & Provenance Contract remains the next artifact.
