## 1. Purpose

Define what must be recorded, retained, and made attributable for every consequential operation in the Spine. Preserve provenance, make conflicts auditable, and prevent silent source-data overwrites. The source describes this contract as operating after the State-Transition Contract, with authorized events as input, PROMOTE / REJECT / HOLD as processing outcomes, and an immutable audit trail as output.

## 2. Core principles

| Principle | Source requirement |
|---|---|
| Accepted events are immutable | No updates, only new events |
| Provenance is append-only | History grows, never shrinks |
| Source authority is preserved | Original system attribution is maintained |
| Rejected and held events are auditable | DENY and HOLD emit full audit records |
| No silent overwrites | Conflicts preserve both claims |
| Audit enables reconstruction | Any state at any time is replayable |

These are draft design requirements, not verified implementation claims.

## 3. Event identity

The source assigns `event_id` on first receipt, preserves the origin's `source_event_id`, and proposes hash chaining for tamper evidence:

```typescript
interface SpineEvent {
  event_id: string;            // UUID v7, assigned by Spine on first receipt
  coordination_id: string;     // Coordination instance
  source_system: string;       // e.g., "epic.prescriber", "surescripts"
  source_event_id: string;     // Preserved from origin, never modified
  source_authority: Authority; // PRESCRIBER | PHARMACY | PAYER | PATIENT
  event_type: EventType;       // PRESCRIBED, DISPENSED, CLAIM_PAID, etc.
  actor_id: string;
  actor_role: string;
  timestamp: string;           // RFC3339 source timestamp
  received_at: string;         // RFC3339 Spine ingest time
  payload_hash: string;        // SHA-256 of canonical content
  previous_event_hash: string | null; // Tamper-evident chain
  content: object;             // Canonical JSON, normalized
}
```

Once `event_id` is assigned, the source describes the entire record as write-once. Corrections arrive as new events with their own source event identifiers referencing the original.

`Authority` and `EventType` are unresolved conceptual types in this draft, not implemented declarations.

## 4. Ordering

Events may arrive out of order. The draft proposes:

| Precedence | Input | Source description |
|---|---|---|
| 1 | `source.timestamp` | Primary clinical time |
| 2 | `source.sequence_number` | If provided by origin |
| 3 | `previous_event_hash` | Causal link |
| 4 | `received_at` | Spine ingest tiebreaker |

The draft defines `current_state` as the fold of ordered, authorized, promoted events only. Rejected and held events do not contribute to verified state. Ordering and causality details remain subject to the discrepancy review; these labels do not override the existing stale/conflict guards.

## 5. Provenance graph

Every promotion references:

- Triggering `event_ref`.
- `authorization_decision_ref`.
- `transition_decision_ref`.
- `prior_state_ref`.
- `resulting_state_ref`.

The source illustrates a directed acyclic graph with source events PRESCRIBED and DISPENSED, authorization and transition decisions, and an illustrative state labeled ACTIVE. Its stated edge sequence is `event_ref → authorization_decision_ref → transition_decision_ref → prior_state_ref → resulting_state_ref`. The exact graph topology and ACTIVE label require reconciliation with the current state model.

## 6. What must be retained

| Outcome | Source retention requirements |
|---|---|
| PROMOTE | Full immutable event; authorization decision with authority basis; transition decision with guard evaluation; promotion record; prior/new state snapshots; responsibility change; provenance references for the full chain |
| REJECT | Full immutable event; authorization decision; transition decision with reason; attempted from/to state; record of no state change |
| HOLD | Full immutable event; authorization and transition decisions; applicable conflict record; promotion-blocked flag; unresolved guards; competing source events |

Full-payload retention is proposed by the source, but permitted storage, scope, and access policy remain unresolved and the existing authority contract's retention boundary continues to apply.

## 7. Duplicate detection

The draft proposes the following idempotency-key construction:

```text
idempotency_key = SHA256(
  source_system + "|" +
  source_event_id + "|" +
  coordination_id + "|" +
  event_type
)

// On match:
// → emit AuditEvent(action_type=DUPLICATE_EVENT)
// → return existing event_id
// → no new state, no promotion
```

The delimiter encoding and audit action enum mismatch are recorded for reconciliation. The existing transition contract continues to reject a second promotion attempt without creating a new state or handoff; incompatible content under the same identity remains an unresolved identity conflict.

## 8. Conflict evidence

Retain all conflicting events with full payloads, each authority basis, timestamps, reconciliation inputs, governing-source determination, non-governing source claims, resolution time, and resolving actor.

| Field | Source retention requirement |
|---|---|
| `conflicting_events[]` | Full payloads, not references |
| `authority_basis[]` | Per-event authority rationale; the source example names PRESCRIBER versus PHARMACY |
| `winning_source` | Determination and timestamp |
| `losing_sources[]` | Never deleted; marked superseded |

The labels `winning_source` and `losing_sources` come from the draft. They do not imply a universal vendor hierarchy or permit silent mutation of immutable source claims.

## 9. Closure evidence

For CLOSED, retain `closure_basis`, referenced milestone events, follow-up completion evidence, final null responsible actor, `closed_at`, `closure_reason`, and full provenance from PRESCRIBED to CLOSED.

Evidence requirements remain branch-specific under the data model: the no-PA branch must not fabricate a payer approval. Closure remains successful coordination completion only.

## 10. Audit event structure

Every decision, including DENY and HOLD, must emit an audit record according to the draft:

```typescript
interface AuditEvent {
  audit_id: string;          // UUID
  timestamp: string;         // RFC3339
  actor: string;             // actor_id
  organization: string;
  patient_ref: string;       // Pseudonymized
  action_type: 'EVENT_RECEIVED' | 'AUTHORIZATION_EVALUATED' |
    'TRANSITION_EVALUATED' | 'STATE_PROMOTED' |
    'STATE_REJECTED' | 'STATE_HELD' |
    'CONFLICT_DETECTED' | 'RECONCILIATION_PERFORMED' | 'CLOSED';
  resource_type: 'SpineEvent' | 'CoordinationState';
  resource_id: string;
  decision: 'ALLOW' | 'DENY' | 'HOLD';
  reason_code: string | null;
  authority_basis: string | null;
  consent_basis: string | null;
  prior_state: string | null;
  resulting_state: string | null;
  provenance_refs: string[]; // event_id, decision_ids
  payload_hash: string;
}
```

This is preserved as a draft code example. It currently omits DUPLICATE_EVENT from `action_type` and does not separately represent the transition-result enum.

## 11. Immutability and retention

The source proposes immutable events, decisions, and promotions through an append-only log with cryptographic hash chaining. It states a minimum retention period of seven years or the applicable regulatory requirement, prohibits hard deletion, and records revocation as a new event.

It further proposes `event_type = REVOKED`, referencing the original via `previous_event_hash`, and says physical deletion violates the contract. These retention/deletion statements are preserved draft proposals, not verified legal requirements or a ratified policy. They require explicit reconciliation with permitted retention and the distinction between an append predecessor and an event being revoked.

## 12. Reconstructability

The proposed API reconstructs current and historical states by replaying ordered, promoted events from genesis:

```text
reconstruct_state(coordination_id, as_of_timestamp)

// Source example:
reconstruct_state("coord_abc123", "2025-12-15T14:30:00Z")
```

The source's Run control is illustrative; no runtime reconstruction is provided by this import. Source-effective time, receipt time, and promotion time need a defined historical-query interpretation.

## 15. Invariants

- No event deletion; append-only log.
- No silent overwrite; conflicts preserve both claims.
- Every promotion attributable to a source event.
- Every HOLD attributable to an unresolved guard.
- Every CLOSED attributable to closure evidence.
- Provenance preserved across conflicts.
- Complete audit trail for PROMOTE, REJECT, and HOLD.

These reproduce draft invariants subject to the pending retention/access and cross-contract review. The source footer says “Draft for Implementation” and “Immutable once ratified.” Repository inclusion records the draft; it does not ratify it or prove any invariant through execution.
